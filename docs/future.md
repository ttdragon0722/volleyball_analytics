## 1. 資料規劃：如何擴展到新場景

### 1.1 可用的資料

| 代號 | 場景 | 預期難度 | 原因 |
|---|---|---|---|
| A | 原場景、側面低角度（同一天的其他影片） | 低 | 跟訓練資料幾乎一樣 |
| B | 同場景、正後方偏低 | 高 | 構圖完全不同，對面球隊被遮擋，從後方看不清楚「球越網」 |
| C | 不同場地、同角度 | 中低 | 只有背景不同 |
| D | 天黑室外、同角度 | 高 | 雜訊多、動態模糊；場邊人多；電燈很亮，周圍過曝 |
| — | 轉播畫面 | 不納入 | 跟目標應用不同，見 §1.4 |

### 1.2 流程

1. **每種場景留 1 部測試影片，永遠不拿來訓練**（A 用 1-3）。測試影片要標得特別仔細，之後每一版模型都用它比較。
2. **用 v2 測每種場景**，整理成「場景 × macro-F1 / 發球 recall」的表。
3. **從最差的場景開始補 1–2 部訓練影片**，用最新模型預標再修正，然後訓練下一版。
4. **每一版都重測所有場景**，確認 A 沒有退步。
5. 同場景的影片（A）最後再補。效益最小，比例太高還會讓模型依賴特定背景。

### 1.3 一個模型還是分場景？

**先用一個模型。** 判斷的目標相同，只是畫面外觀不同；混在一起訓練，模型通常學得更通用。下游的剪輯也只要用一個模型。
只有在補了 3 部以上的資料後，某個場景（最可能是 B）仍明顯拖累其他場景，才考慮從通用模型接續微調一個專用版本。

### 1.4 天黑場景的標註重點

| 問題 | 可能的誤判 | 處理 |
|---|---|---|
| 場邊人多 | 有人走動或撿球，被判成「比賽中」 | 確實標成「非比賽」，讓模型學到只有場上的人在動才算 |
| 雜訊多、動態模糊 | 看不到球，發球邊界不準 | 用球員動作判斷（準備發球的姿勢、對面接球） |
| 電燈很亮 | 過曝區域閃爍 | 多標幾部天黑影片 |

評估後看混淆矩陣：「非比賽」被判成「比賽中」比較多，主要是人群造成的；「發球」漏掉比較多，主要是畫面看不清楚造成的。

### 1.5 轉播畫面不納入訓練

目標應用是「匯入自己打球的影片就能分析」，訓練資料越接近這種畫面越好。轉播的鏡位、剪接、比分條、球員水準都不同；重播和特寫在現有規範裡無法標註；而且會分散小模型的學習容量。
只有在自己的資料用完、模型某個動作仍學不會時，才挑少量**固定鏡位、沒有剪接**的片段當作補充，而且不放進測試集。

### 1.6 規定拍攝方式

比起收集各種畫面，**規定使用者怎麼拍**更有效：例如手機固定架在場邊側面或端線後方的斜角、高度至少多少、整個球場都要入鏡。可以出現的畫面種類被限制住，有限的資料就能涵蓋大部分情況。

### 1.7 訓練工具待補的功能

- [ ] **按場景平均抽樣**：現在每類固定抽 400 個樣本，影片多的場景會被抽到比較多次。
- [ ] **按場景出成績表**：一個指令評估多部測試影片，每種場景輸出一行結果。

## 2. 比賽狀態偵測的應用

比賽狀態偵測的核心價值，是**把整場比賽切成一分一分**。這是之後所有分析的基礎。

### 2.1 只靠狀態就能做

| 應用 | 說明 |
|---|---|
| 自動剪輯 | 已有 `game_state_clipper` |
| 節省運算資源 | 只在比賽中才跑球追蹤、姿態估計 |
| 比賽節奏統計 | 每分長度、分與分的間隔、實際打球時間的比例、每局的節奏變化（體能指標） |
| 精華自動挑選 | 挑最長、來回最多的幾分 |
| 章節標記 | 輸出成 YouTube 章節、剪輯軟體的標記、播放器的「跳到下一分」 |
| 只看特定情境 | 例如把所有發球加接發球抓出來 |

### 2.2 加少量資訊能做的

| 應用 | 需要的額外資訊 |
|---|---|
| **自動記分** | 發球在哪一側。發球權換邊，代表接發球方得分，就能推出比分和輪轉 |
| 發球分析 | 人物辨識。統計每人的發球數，發球後很快結束的分可能是得分或失誤 |
| 下游模型的開關與分段 | 每分開始時重置追蹤器，減少把場邊的人或球誤判成比賽動作 |
| 自動產生標註資料 | 自動切好的每一分，可以直接拿來標動作 |
| 即時標記 | 直播或錄影時自動打書籤，或只錄比賽中的片段 |

**自動記分**最有價值：不用再標新資料，只多判斷「發球在哪一側」。

## 3. 正後方偏低角度

### 3.1 根本問題：遠處的地面被壓扁

鏡頭越低，每個像素代表的地面距離跟距離的平方成正比。
粗估：1080p 手機、焦距約 1500 px、鏡頭高 1.2 m、在端線後 2 m。

| 位置 | 距離 | 1 px 約等於 | 腳點偵測誤差 5–10 px 時 |
|---|---|---|---|
| 己方前區 | ~5 m | 1.4 cm | ~10 cm |
| 網子附近 | ~11 m | 7 cm | ~0.5 m |
| 對方底線 | ~20 m | 22 cm | 1–2 m |

再加上對面球員的腳常被己方擋住，平面化需要的腳點直接消失。

### 3.2 結論：精確分析己方，對面只做粗略分析

| | 己方（精確） | 對方（粗略） |
|---|---|---|
| 位置 | 2D 座標、陣型、跑動距離 | 前排或後排、左中右分區 |
| 事件 | 接發、舉球、攻擊的位置和品質 | 從哪一區攻擊、球落在己方哪裡 |
| 推論方式 | 直接偵測 | 用己方的反應反推 |

- 校正點只用近端：己方的底線角、3 m 攻擊線兩端、中線和邊線的交點，加上球場尺寸 9×18 m。
- 被擋住的腳點：用 Kalman 追蹤補位置，補不了就標成「位置不確定」。
- 雙方都要精確，唯一可靠的做法是另一端再架一台，或改成高位置的側拍。

### 3.3 改善方法（依效果排序）

1. **從拍攝方式改善**：鏡頭架高到 2.5–3 m，或改到端線後方的斜角（30–45°）。
2. **跨視角轉移標籤**：如果正後方和側拍是同一場、同時錄的，用聲音對齊時間後，把側拍的標籤直接套到正後方影片。**要先確認資料是不是同時錄的。**
3. **讓模型利用看得到的線索**：前排球員的反應、飛高的球、聲音。
4. **時序規則**（HMM / Viterbi）：比賽狀態有固定順序（非比賽 → 發球 → 比賽中 → 非比賽），每種狀態也有合理的長度。所有角度都受益，而且不用重新訓練。
5. **訓練上的調整**：加「不確定」標記並在訓練時跳過；先裁掉天空和地面，只保留球場的區域再縮小到 224；這個角度的發球定義可以放寬。

## 4. 聲音

### 4.1 球場上的聲音線索

| 聲音 | 特徵 | 代表什麼 |
|---|---|---|
| 擊球聲 | 很短的「啪」，中高頻能量很強 | 比賽中大約每 1–2 秒一次 |
| 發球擊球 | 一段安靜後的第一個強擊球聲 | 發球的時間點（發球開始 = 擊球前約 1 秒） |
| 球落地 | 較低沉的「咚」 | 這一分大概結束了 |
| 哨音 | 單一音高，持續 0.3–1 秒 | 開始或結束，但業餘比賽常沒有裁判 |
| 歡呼、說話 | 連續、雜亂 | 得分後的非比賽時間 |

### 4.2 聲音模型的四種用法

| 用法 | 做法 | 需要的資料 |
|---|---|---|
| 1. 訊號處理 | 過濾 1 kHz 以下 → onset detection（`librosa`）找擊球聲 | 不用訓練 |
| 2. 現成模型直接判斷 | CLAP（聲音對文字）；YAMNet、PANNs（AudioSet 527 類，已有 Whistle、Cheering 等） | 不用訓練 |
| 3. 預訓練特徵＋小分類器 | PANNs、BEATs、AST 抽 embedding，模型不動，只訓練一個 MLP | 現有標籤直接用 |
| 4. 跟影片融合 | 後期融合（兩邊的機率加權平均，建議先做）或特徵融合（特徵接在一起） | 現有標籤 |

```
影片 ─► VideoMAE ───────────────► 3 類機率 ┐
                                           ├─► 加權平均 ─► 時序規則 ─► 狀態片段
音軌 ─► PANNs/BEATs ─► 小 MLP ──► 3 類機率 ┘
     └► onset 偵測 ─► 擊球時間點 ──────────► 修正發球的開始
```

另一個用途：在標註工具的時間軸下面加一條聲音波形，標發球起點會更快、更一致。

### 4.3 會遇到的問題

- **隔壁場的聲音**：擊球聲幾乎一樣，手機的單一麥克風分不出方向。這是最大的問題，一定要跟影像一起判斷。
- 室外風聲：濾掉低頻後大部分可以去掉。
- 業餘比賽沒有裁判吹哨。
- 抽音軌時要確認影音沒有偏移。

### 4.4 類似的應用

| 領域 | 例子 |
|---|---|
| 板球 | DRS 的 Snickometer / UltraEdge，用聲音判斷球有沒有擦到球棒，是正式判決的依據 |
| 高爾夫 | 部分設備用擊球聲音觸發高速攝影 |
| 轉播精華 | 用觀眾歡呼聲和主播的激動語調找精彩時刻 |
| 棒球 | Rui, Gupta & Acero（ACM MM 2000）：用球棒擊球聲加上主播的激動程度做精華 |
| 足球 | Vanderplaetse & Dupont（CVPR Workshop 2020）：SoccerNet 動作偵測加入聲音後準確率提升 |
| 通用 | Audio-Visual Event Localization（Tian et al., ECCV 2018，AVE 資料集）；Audiovisual SlowFast（Xiao et al., 2020） |
| 球拍類運動 | 桌球、網球、羽球有不少用擊球聲偵測擊球時間的研究 |

這些研究多數用的是**轉播音訊**，收音乾淨、只有一個場地；這裡用的是業餘手機錄音，雜訊大很多。

### 4.5 第一步：先確認聲音有沒有用（約 1 小時）

用 1-3 抽出音軌，跑 onset 偵測和 YAMNet，畫在標籤時間軸上，看兩件事：
1. 每個發球段裡面，有沒有一個清楚的擊球尖峰？
2. 隔壁場和人聲的干擾有多嚴重？

## 5. 轉播畫面的處理

```
轉播影片 ─► 鏡頭切換偵測 ─► 鏡頭分類 ─┬─ 主鏡頭 ──► 球場校正 ─► 比賽狀態 / 2D 分析
                              │       ├─ 特寫、觀眾、教練 ─► 略過
                              │       └─ 回放 ─► 略過（避免同一分算兩次）
                              └─► 比分條 OCR ─► 比分變化 = 每分結束的時間點
```

### 5.1 角點出畫面

- 用兩條線的交點找回角點是可行的，但**兩條線接近平行時，交點非常不準**。
- 更穩的做法：**直接用線算 homography**。所有看得到的點和線一起用最小平方法求解，再用 RANSAC 排除偵測錯的線。
- 鏡頭會移動和縮放：用前後幀的特徵點匹配（ORB）或 ECC 逐幀追蹤，再定期用場線重新校正，避免誤差累積。
- 參考：SoccerNet Camera Calibration 挑戰賽；網球和籃球都有用模型偵測球場關鍵點的做法。
- 比分條和台標要先遮掉。網子不在地面上，不能拿來算地面的 homography，但網高（男 2.43 m、女 2.24 m）可以當作 PnP 的校正點。

### 5.2 鏡頭切換與回放

| 任務 | 方法 |
|---|---|
| 鏡頭切換 | 色彩直方圖差異（最快）→ **PySceneDetect**（建議先用）→ **TransNetV2**（淡入淡出也抓得到） |
| 判斷是不是主鏡頭 | 球場地板顏色的比例、場線校正是否成功、小分類器或 CLIP zero-shot |
| 回放 | **回放轉場的 logo 動畫**（樣板比對，最可靠）、比分條消失、慢動作的重複幀、不同角度的鏡頭 |

### 5.3 比分條提供免費標籤

對比分條做 OCR：數字改變就代表上一分剛結束。可以自動得到每分結束的時間點和比分，完全不用標註。

## 6. 空中的球與跳起來的人

### 6.1 為什麼不能直接轉

Homography 只對地面上的點有效。空中的球在畫面上的一點，對應到真實世界是一整條從鏡頭射出的線，單看一幀分不出深度。

### 6.2 方法

**方法 1：只在著地的那一刻轉換（最簡單，先做這個）**
- 落地點：偵測反彈的那一幀，直接用 homography。
- 擊球點：用擊球者的地面位置代表，誤差大約 1 m。擊球時間用軌跡方向突變或擊球聲判斷。
- 就能畫出「誰從哪裡打到哪裡」的 2D 箭頭，涵蓋大部分的分析需求。

**方法 2：用物理推算 3D 軌跡**

```
X(t) = X0 + Vx·t
Y(t) = Y0 + Vy·t
Z(t) = Z0 + Vz·t − ½·g·t²      g = 9.8 m/s²
```

- 6 個未知數，每一幀提供 2 個方程式。60 fps 下一段軌跡有幾十幀，用最小平方擬合。
- **重力是已知的，提供了真實的尺度**，所以單一鏡頭也能推出深度。
- 需要：完整的相機參數（場線加網高做 PnP）、球的 2D 偵測（TrackNet 類）、用擊球點把軌跡切段。
- 可以得到：落地點、過網高度、最高點、球速、飛行時間。
- 要注意：飄球和高速發球要考慮空氣阻力；正後方角度的深度誤差比側拍大。

**方法 3：跳起來的人**
- 用姿態模型（YOLO-Pose、RTMPose）判斷腳踝是否離地。
- 騰空期間用**起跳點**代表位置，有需要再跟落地點做線性插補。
- 跳躍高度：
  - 用滯空時間 t 推算 **h = g·t² / 8**，不需要相機校正，60 fps 下精度約幾公分。
  - 或用起跳點的深度換算「1 m 等於幾個像素」，量臀部升高了多少。

**方法 4：兩台攝影機**
- 用三角測量直接算出 3D 位置，不需要物理假設。
- 兩台手機架在不同位置，用擊球聲同步，誤差可以在一幀以內。

### 6.3 建議順序

| 步驟 | 內容 | 能回答的問題 |
|---|---|---|
| 1 | 球偵測＋擊球點偵測 | 球在畫面哪裡、什麼時候被打 |
| 2 | 落地點＋擊球者位置 → 2D 箭頭 | 球從哪裡打到哪裡 |
| 3 | 姿態模型＋滯空時間 | 起跳位置、跳躍高度 |
| 4 | 物理擬合 3D 軌跡 | 球速、過網高度 |
| 5 | 兩台攝影機 | 高精度 |

## 7. 讓產品有創意的方向

目標使用者是「打球的一般人」，不是職業球隊。職業隊已經有專人用 Data Volley 這類軟體做統計；**一般人沒人幫他們做，這正是機會。**

### 7.1 對個人：上傳影片就拿到「我的比賽報告」

- **個人精華**：辨識每個球員（背號、衣服顏色、Re-ID），自動剪出「我的所有扣球」「我的所有接發」。
- **社群短片**：自動輸出直式的 IG Reels 或 Shorts，鏡頭跟著球裁切，加上比分和慢動作。這是最容易讓人主動分享、帶來新使用者的功能。
- **成長紀錄**：跨場次追蹤跳躍高度、發球成功率、接發品質。「這個月你的平均起跳高了 4 公分」。

### 7.2 對隊伍：像職業隊一樣的數據

- **自動記分表＋輪轉分析**：「第 4 輪轉失分最多」「這個人站位時接發成功率最低」。
- **正負值（plus/minus）**：誰在場上時球隊得分比較多。這不需要辨識每個動作，只需要知道誰在場上和每分的結果。
- **發球落點與攻擊路線的熱圖**：用 §6 的 2D 箭頭累積。
- **戰術板動畫**：把追蹤到的位置畫成俯視動畫，可以拖拉時間軸，教練可以直接拿來講解。

### 7.3 用 LLM 做「會講話」的分析

- **自動賽後總結**：把事件紀錄（每分的比分、發球者、得分方式）交給 LLM，產生文字回顧。例如：「第二局 18:20 之後連續三球發球得分，逆轉關鍵在……」
- **用自然語言搜尋影片**：「找出所有我扣球被攔的球」「第三局所有超過 10 秒的分」→ 轉成查詢事件資料庫，直接跳到片段。
- **個人化建議**：根據統計結果給練習方向，例如接發都偏向左側。

### 7.4 現場與社群玩法

- **手機即時記分板**：手機架在場邊，自動記分、自動只錄比賽中的片段，可以投到大螢幕或直播疊加比分。
- **揪團打球的排行榜**：常一起打球的人累積個人數據，做賽季排行和成就徽章，增加持續使用的動機。
- **多手機協作**：朋友各自用手機拍，用擊球聲自動同步，合成多視角，甚至做 3D 重建（§6 方法 4）。

### 7.5 資料飛輪

使用者在 App 裡修正錯誤的標籤 → 自動回收成訓練資料 → 模型越用越準。
現在的標註工具（預標、修正、存檔、再訓練）就是這個飛輪的雛形。之後可以加入**主動學習**：只請使用者確認模型最沒把握的片段。

## 8. 發展路線圖

| 階段 | 目標 | 主要工作 |
|---|---|---|
| **P0 穩定比賽狀態** | 4 種場景都可靠 | 各場景測試集、補資料、時序規則、聲音驗證與融合 |
| **P1 自動剪輯＋記分** | 第一個可用的產品 | 發球方向判斷 → 自動比分；精華挑選；章節輸出 |
| **P2 追蹤與 2D 分析** | 球去哪裡、人在哪裡 | 球偵測、擊球點、落地點、姿態、跳躍高度、熱圖 |
| **P3 個人化與 LLM** | 讓人想用、想分享 | 球員辨識、個人報告、社群短片、賽後總結、自然語言搜尋 |
| **P4 進階** | 更精確、即時 | 3D 軌跡、多手機協作、即時記分板、主動學習 |

### 接下來最直接的幾步

1. 標 B、C、D 各 1 部測試影片，用 v2 實測，整理每種場景的成績表。
2. 訓練工具加上「按場景平均抽樣」和「按場景出成績表」。
3. 在模型預標後面加上時序規則。
4. 用 1-3 驗證聲音有沒有用（約 1 小時）。
5. 確認正後方影片是不是跟側拍同時錄的，如果是，就做跨視角標籤轉移。
